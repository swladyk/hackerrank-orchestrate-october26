# Evaluation Report — Ghost Data Still Exists deletion-audit agent

## How the evaluation was run

* **Labelled data:** the 32 public cases (`dataset/sample_deletion_requests.csv` → `dataset/sample_output.csv`)
  plus 4 custom cases we built (`code/evaluation/custom_cases/`). The 518 evaluation cases have hidden answers
  and were only checked structurally (see below).
* **Command:** `uv run code/evaluation/main.py --verbose --write-report` — runs the agent end to end on the
  labelled requests and scores the predictions; the metrics block below is generated by that command.
* **Metrics** (`code/evaluation/main.py`):
  * *case-level status accuracy* — `deletion_status` equal;
  * *step-level precision / recall / F1* — steps matched as a multiset on
    (phase, system_id, resource_id, operation, state, evidence_id); also reported ignoring `evidence_id`;
  * *field-level accuracy* — steps aligned by array position (the grader keeps array order), each of the 7
    fields compared, missing/extra positions count as wrong;
  * *sequence accuracy* — the whole `steps_json` array exactly equal (order included).
* **No answer leakage:** the agent never reads `sample_output.csv`; all rules are generic (no case ids, no
  per-case constants). The sample answers were used only to measure and to understand conventions
  (ordering, which evidence is cited, what counts as in scope).

### Structural checks on the full 518-case run

`output.csv` has exactly 518 data rows sorted by `case_id`, the exact header, valid JSON in every
`steps_json`, consecutive `step_no` from 1, phases in FINDING → REMEDIATION → VERIFICATION order, only the
allowed operation/state pairs, `[]` for every `NOT_APPLICABLE`, empty `evidence_id` on every remediation step and
on every verification step of an `INCOMPLETE` case, and no cited file captured after the case's `audit_at`.

## Failures found and improvements made

Measured on the 32 samples, offline mode (rule-based intent, no screenshots), step F1 over all six fields:

| # | Change | Status acc. | Step P / R / F1 | Sequence acc. |
|---|---|---|---|---|
| 0 | First end-to-end pipeline (identifier links only) | 87.5% | 100 / 72.5 / 84.1 | 25.0% |
| 1 | Log reads / PII scans count as "record exists"; intent fallback fixes (`close this account`, `is gone`, false `copy of` negation) | 96.9% | 100 / 83.9 / 91.3 | 34.4% |
| 2 | Link identifier-less records (deleted accounts, anonymized analytics) through the deletion worker's job; prove absence from complete snapshot listings | 96.9% | 95.7 / 93.3 / 94.5 | 62.5% |
| 3 | Job anchor must match the claim (SUCCESS↔COMPLETE, PARTIAL↔PARTIALLY_COMPLETE, FAILED↔NOT_STARTED); non-deletion requests do not compete for jobs | 96.9% | 96.3 / 94.3 / 95.3 | 68.8% |
| 4 | Policy actions only go to jobs with a compatible logging style (all-before-report vs results-after-report), learned from evidence-attributed actions | 96.9% | 98.9 / 95.3 / 97.1 | 84.4% |
| 5 | PDF text extraction + catalog alias resolution (`support_001` attachment in a PDF) | **100%** | **99.5 / 97.4 / 98.4** | **87.5%** |

Other failures found along the way:

* **Six log formats.** Key-value, syslog, JSON, bracketed, pipe-delimited and nested `message="…"` lines; the first
  parser read only one. A format-agnostic line normalizer fixed every file (all 26 logs now yield observations).
* **Trace-level linking.** Many log completions carry only `resource_id`; the subject appears on the
  `*_started` line of the same trace (`lookup_key`, `subject_ref`, `correlation_key`). Linking by trace id fixed
  `audit_record_4902` / `account_3960` in `case_09`.
* **File capture time vs record time.** Some logs were exported after `audit_at` but record events before it.
  Facts are used if *recorded* by `audit_at`; only files *captured* by `audit_at` are cited. When the only
  direct observation is uncitable, absence is proven by the newest citable complete listing of that system.
* **Out-of-scope history.** `case_17`'s user has an older request (`case_46`); a March lookup of a different
  account would have produced a wrong extra step. Records must be observed between `requested_at` and
  `audit_at` to be in scope.
* **Decoys.** Similar names/emails (`Jonas Berg` vs `Jonas Berglund`) are never fuzzily matched — only exact
  normalized identifiers (email case-folded, phone digits, accent-folded names, SHA-256 email hashes).
* **custom_02 in offline mode.** The rule-based fallback sees *supprimer* and wrongly returns a deletion; the
  Decisions-API classifier is required for negated, non-English requests (this is why the fallback is only a
  fallback).

## Known limitations

* **Undiscoverable records.** Two sample answers verify audit records (`audit_record_6645`, `audit_record_5569`)
  that appear in no participant-visible file; no evidence-based system can produce them.
* **Concurrent identical jobs.** When several requests report at the same minute with the same claimed status,
  the account submissions / policy actions that carry no identifier cannot be told apart from the visible data
  (e.g. `case_23`: `account_410` vs `account_7015`). The agent assigns them first-come-first-served by
  `case_id`. Because sample ids are lower than evaluation ids, this tie-break favours the samples, so the
  sample scores above are an optimistic estimate for those ambiguous situations in the hidden set.
* **Hand-made sample edge cases.** `case_04` verifies an account and an analytics report that no activity or
  identifier ties to the user; we did not special-case it.
